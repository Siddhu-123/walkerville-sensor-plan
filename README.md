# Walkerville Sensor Plan

A guided Simulation 4 demo for Capstone PG-S2-22, *Optimal Sensor Placement for Wastewater Network Monitoring*, at Adelaide University with SA Water.

**Live demo:** https://siddhu-123.github.io/walkerville-sensor-plan/demo.html

The GitHub Pages link serves the `main` branch. Local changes appear there after they reach `main` and Pages publishes them.

The deck uses Simulation 4 from `gravity-sewer-osp main @ 10e6852`. It has a welcome page plus 8 scenes on one map of Walkerville. It explains wet-weather loading, growth, region triage, sensor choices and the data needed before deployment.

## What it shows

- Wet weather already surcharges pipes before growth. On a design wet day, 2041 growth newly surcharges no manhole. The model's 11 region-weather overload pairs occur in wetter cases.
- Eight regions hold near-equal numbers of existing homes. R9 is the overlapping Walkerville Terrace corridor. The region method is adapted from Kim et al. (2022), with cuts at pipe ends, loops included and overlapping manholes allowed. The original paper concerns disease surveillance.
- Triage uses the design wet case: monitor R3 and R7, watch R1, R4 and R9, and leave R2, R5, R6 and R8. Only R5 keeps room in all 7 wet cases.
- One level sensor sees all 16 design wet growth runs. The nested five-sensor plan sees 94% on average and 81% in the worst wet case across 7 wet cases, using an assumed 10 mm rise rule. At 25 mm, those figures fall to 45% average and 36% worst.
- With five sensors, coverage falls to 77% on unseen weather and 76% on an unseen region. R9 overlaps other regions, making the unseen-region result a little generous.
- Floats alone reach 35% average and 0% worst coverage. At a $75k budget, a mix of 2 level sensors and 6 floats costs $56k and reaches 62% worst coverage, compared with 44% for 3 level sensors. Prices and the 25 mm float margin are assumed.

These are uncalibrated model results. The rise rules, pipe limit and prices are assumed. Wet-weather level records are needed to decide between one sensor and five. The model does not include long-term sensor failures. The 485-home planning anchor comes from the Simulation 4 export; the underlying planning projection is still needed.

## Scenes

The welcome page is followed by these 8 scenes:

| Scene (`#id`) | Topic |
|---|---|
| `problem` | Wet-weather loading before growth |
| `changed` | Changes since the October demo |
| `regions` | Which regions to monitor, watch or leave |
| `sensors` | One sensor for design wet, five for wetter weather |
| `type` | Level sensors and float switches at assumed budgets |
| `holdup` | Performance on unseen weather and regions |
| `assumed` | Assumptions, limitations and missing data |
| `close` | Start with one level sensor in R3, then grow to five |

## Data and files

The deck's numeric facts and chart series come from `demo/sim4-facts.js`. Region membership, triage and baseline surcharge locations come from `demo/sim4-regions.js`, generated by `demo/tools/build_sim4_regions.py`. Both use the saved Simulation 4 exports in `demo/notes/sim4_source/sim4.js` and `demo/notes/sim4_source/regions.js`. The generator also uses `chambers_index.json` there to translate manhole indices into IDs.

| Path | Purpose |
|---|---|
| `demo.html` | Page shell, map, sidebar and controls |
| `demo/scenes.js` | Welcome page, 8 scenes and camera cues |
| `demo/sim4-facts.js` | Numeric facts, sensor ladder and chart series |
| `demo/sim4-regions.js` | Generated region membership, triage and baseline locations |
| `demo/tools/build_sim4_regions.py` | Generates the region file from saved source data |
| `demo/engine.js` | Map rendering, fact tokens, charts and interactions |
| `demo/story-data.js`, `demo/pump-data.js` | Generated network geometry, baseline arrays and pumps |
| `demo/sources.js` | Citations and detail cards |
| `demo/basemap.js`, `demo/basemap-data.js` | MapLibre basemap and bundled geographic layers |
| `demo/demo.css`, `demo/welcome.css` | Styles and themes |
| `demo/notes/sim4_source/` | Saved Simulation 4 source exports |
| `vendor/` | MapLibre GL JS |

## Run locally

From the repository root:

```sh
python3 -m http.server 8766
```

Open http://localhost:8766/demo.html.

The "Open Simulation 4" link opens the [Simulation 4 workbench](https://abrahampaulj.github.io/gravity-sewer-osp/simulation4/index.html).

## Run the checks

Python 3, Node.js and zsh are required. From the repository root:

```sh
zsh demo/notes/check_deck.sh
```

This runs JavaScript syntax checks and `python3 demo/tools/check_facts.py`, requires exactly 9 scene objects (welcome plus 8), and checks writing rules, team names and limitations copy. It does not test browser layout or interactions.

To check the data alone:

```sh
python3 demo/tools/check_facts.py
```

The facts check requires every numeric value in `facts`, `curves`, `budget_compare` and `holdout_k5`, including numbers inside strings, to appear in the saved source exports. It allows percent/fraction conversion rounded to whole percent and equivalent money formats. Any derived exceptions must be listed with a reason in the script's `ALLOW` mapping. This checks that numbers appear in the source; it does not verify their meaning in each claim.

The check also runs the region generator in a temporary directory and compares its output byte for byte with `demo/sim4-regions.js`. It leaves the tracked file untouched. To regenerate that file intentionally:

```sh
python3 demo/tools/build_sim4_regions.py
```
